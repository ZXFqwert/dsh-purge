# DSH 0.2.1-rc.2 compatibility work

Status: experimental, not a release or a security sandbox. Original upstream attribution and license are retained.

## Changes under test

- Match the 0.2.1 web environment URL description, the prompt assembler's required-context filter, and the conversation append implementation.
- The prompt assembler replacement retains required contexts when runtime-context suppression is active.
- Use a static persona suffix: `{{cwd}}` is not registered in some headless profiles.
- In explicit isolated mode, restrict host discovery and patch targets to the configured laboratory, suppress global launcher modifications and DSH Doctor cleanup, and reject a different explicit DSH target.
- Create backups with exclusive copy rather than a Windows-incompatible rename over a placeholder. Abort a multi-host apply when backup reports errors.
- In isolated development mode, block the built-in destructive updater and uninstall; use the separate Git checkout for development instead.
- The red-team UI has a separate npm/pnpm updater: isolated mode blocks both update checks and installation before preflight or child-process launch, while keeping local version information available. Authenticated Web API tests confirmed both blocks and a working bootstrap.
- Isolated rules, skills and red-team writes check existing path ancestors for junctions escaping the lab; red-team skill synchronization excludes the ordinary user home. Archive skill imports are disabled in isolated mode pending safe extraction review.
- Plugin, rule, skill and red-team HTTP routes use the host connection's authentication check. Unauthenticated requests are rejected; fail closed if the host authentication service is unavailable.
- Isolated Web restarts retain the selected port and Node execution flags rather than falling back to port 3080 or losing the permission flags.

## Local verification

Use a disposable install and home, not your everyday DSH installation. Set absolute `DSH_HOME`, `DSH_BASE` (the runtime's `node_modules/@deepseek-ai`), `DSH_PURGE_LAB_ROOT`, and `DSH_PURGE_ISOLATED=1`. Set `TEMP` to an approved temporary directory, then run `npm run test:compat`.

`scripts/inspect-compat.mjs` inspects matches without writing target files. `scripts/dry-run-patches.mjs` also requires `DSH_RUNTIME_ROOT`, transforms files only in memory and runs syntax checks. These checks do not establish behavioral compatibility.

The fixture scripts under `scripts/` are for disposable, newly created target copies only. Run the apply/revert scripts with Node's permission model, restricting filesystem writes to the fixture and disallowing child processes. Never run a fixture command against a production install.

## Known limits

- `DSH_PURGE_ISOLATED=1` is an application-level guard, **not an OS sandbox**. The plugin has broad host privileges and paths outside the core patching functions require further review.
- Path checks are not atomic against junction changes; SQLite native I/O, other native code and spawned processes are not fully confined by these checks. Do not treat them as a security boundary.
- DSH's loader needs native addons; Node explicitly warns `--allow-addons` can invalidate its permission model. Do not rely on that model alone for isolation.
- A local mocked Messages endpoint can validate prompt injection and a read-tool round trip, not the behavior of a real DeepSeek model or its service rules.
- A controlled local mock was also used to exercise one PowerShell tool round trip; it does not validate arbitrary shell commands.
- Full GUI approval, normal tool permissions, upgrade recovery, and live provider authentication require separate testing before release.
- A user must personally review the first-use notice and complete real DeepSeek sign-in and GUI conversation/tool acceptance. No real credentials were copied or used in the mock tests.
- A local authenticated Web API Apply → restart → status → Revert → manual restart run was tested with a disposable copy: Apply reported 62 changes, post-restart status had 0 pending, and Revert restored 50 changed files. All 55 copied target files matched the pristine originals by SHA-256. After the manual restart, 57 items were pending again, consistent with the restored state. Five stable-install reference files also matched their pre-test hashes. This does not prove every possible filesystem path is confined.
- Unauthenticated requests to status, rules, skills, and red-team routes returned HTTP 401; authenticated rules and skills returned 200; authenticated cross-origin status returned 403. Isolated update and uninstall operations were rejected. Test results apply to the Web profile on Windows and do not establish desktop compatibility.
- After the red-team write guards in commit `6aa456e`, a fresh authenticated 3085 Web API run again applied 62 patches with zero failures, restarted with 61/63 applied and zero pending, and reverted 50 files. All 55 selected target files matched the unpatched source SHA-256, and five stable-install reference hashes remained unchanged. The authenticated red-team `bootstrap` operation succeeded before and after restart and reported the experimental home as its root; this does not constitute a full red-team workflow test.
- A subsequent authenticated red-team Web API test discovered that reopening a database deleted custom stage codes during migration. The migration no longer deletes arbitrary custom stages; explicit legacy stage migrations remain. A new disposable engagement and custom stage were saved, read, and read again with the same marker after a 3085 restart. The original test stage had already been deleted by the old migration and could not be recovered by this fix. Five stable reference hashes and the 3080 process remained unchanged.
- Isolated Windows tests exercised normal screenshot and knowledge entry writes, and rejected outside junctions at screenshot, attack-file, knowledge-entry, and knowledge database paths. Attack-file directory validation now occurs before directory creation. These are targeted tests, not an audit of every write path or concurrent link changes.
- Against commit `7a5db79`, an authenticated isolated Web API test saved and read a 68-byte test image and a knowledge entry; both contents matched after restarting the 3085 service. A later targeted test found that isolated screenshot deletion swallowed a path-guard error and removed its database row; the guard now fails before deleting the row, with a junction regression test. The API persistence test preceded that deletion-only change.
- Against commit `3ee47c4`, authenticated 3085 API tests confirmed normal screenshot deletion removes the file and row, while an outside junction causes rejection and preserves the row; the restored original image remained readable. A separate knowledge deletion audit found the same ordering issue: isolated deletion now checks and removes the directory before removing the row. Targeted tests confirm normal deletion and row preservation on an outside junction; these operations are not atomic against process interruption or link races.
- Against commit `2211067`, authenticated 3085 Web API tests confirmed normal knowledge deletion removed its directory and database row; an outside junction was rejected and the row and outside sentinel remained unchanged. After restoring the test directory, its file and record contents still matched. Five stable reference hashes and the 3080 process remained unchanged.
- A red-team import audit found that `scan_run` was inserted outside the import transaction. It is now inserted inside that transaction. In an authenticated isolated 3085 API test, a deliberately invalid import failed and left no asset; a following valid import created one test asset and one port. A read-only SQLite query found one scan run and one asset total. This tests one import failure case, not all red-team workflows.
- After restarting 3085, the imported test asset was still readable through the authenticated API; read-only SQLite checks found its single scan run and 443 port. A separate isolated unit test saved a custom red-team role prompt, rejected a prompt directory junction outside the lab, and confirmed the original prompt remained unchanged after restoring the directory. Five stable reference hashes and the 3080 process remained unchanged.
- Against `4ef38bd`, an authenticated isolated 3085 Web API test saved and read a role prompt, rejected a write when its prompt directory was an outside junction, preserved the outside sentinel, and read the original prompt again after restoring the directory and restarting. Five stable reference hashes and the 3080 process remained unchanged. The test engagement remains in the disposable test home.
- A targeted isolated unit test saved red-team concurrency settings and platform configuration, rejected both writes when the configuration root was replaced by an outside junction, and verified the outside sentinel and original settings after restoring the directory. A later authenticated Web API test with a separate home on 3086 saved both values and read them back after restart; substituting an outside directory junction at each configuration file caused HTTP 400 while preserving the outside sentinel and restored settings. This is not a process-crash recovery test; those writes are not transactional.
- Engagement IDs now reject path separators and `.`/`..`, preventing calls from targeting another directory outside `engagements`, including another directory within the lab. An authenticated 3085 API test rejected a `../` prompt write without creating its destination and successfully read an existing test engagement. Unit tests passed and five stable reference hashes and the 3080 process were unchanged.
- Against `dc08b06`, an authenticated isolated 3085 API test created a custom score point, read it after restarting, deleted it, and confirmed its absence from the score list. The test used a new disposable engagement; five stable reference hashes and the 3080 process were unchanged. This does not test all score-hit deletion, interruption or concurrent-write scenarios.
- A subsequent isolated SQLite failure-injection test found that deleting a score point could delete its hits even when deleting the point failed. Both deletes now share a savepoint: the test verifies failure preserves both rows, an enclosing transaction can roll the delete back, and a normal deletion removes both. This is a targeted database test, not an end-to-end Web failure test.
- Against `c7357a1`, an authenticated isolated 3085 API test used a trigger in a newly created test database to reject the second deletion: the API reported failure and read-only queries confirmed one score point and one hit remained. After removing the test trigger, API deletion succeeded and both counts were zero. Five stable reference hashes and the 3080 process were unchanged. Other failure and concurrency scenarios remain unverified.
- A screenshot write audit found that a duplicate filename overwrote the original file before the unique database insert failed. Screenshot files now use exclusive creation and a failed database insert attempts to remove the newly created file. An authenticated isolated 3085 API test confirmed duplicate rejection preserved the original bytes and an injected insert failure removed its newly created file. The trigger was removed afterward. This is not an atomic filesystem/SQLite transaction: process interruption, outer transaction rollback, cleanup failure or concurrent path replacement can still leave inconsistencies.
- Against `1196b1f`, the 3085 test process was restarted after the screenshot failure tests: the original test screenshot and bytes remained readable via authenticated API, the failed-insert file remained absent, and read-only SQLite checks found one screenshot and no remaining fault-injection trigger. Five stable reference hashes and the 3080 process were unchanged.
- An isolated unit test now injects a partial screenshot file write followed by an ENOSPC-like exception. Exclusive creation tracks the file descriptor and attempts to remove the partial file on a catchable write or close failure; the test confirms no file or database row remains. A subsequent 3085 authenticated API test confirmed normal save and duplicate rejection. This does **not** simulate process termination or power loss; an uncatchable interruption or failed cleanup can leave a partial file.
- An experimental 3084 instance was restarted against `a66754a`: unauthenticated status, rules, skills and red-team routes returned 401; its authenticated page returned 200, the selected runtime and home were experimental, and patch status was 61/63 applied with zero pending. Red-team bootstrap and the isolated updater guard worked. The stable process and five reference hashes were unchanged. Live account and GUI acceptance remain outstanding.
- `dshTarget` still identifies the original supported target; do not claim general 0.2.1 support based only on these checks.
